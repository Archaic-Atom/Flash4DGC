## 1. 先明确现在的方法

Flash4DGC 是建立在 4DGC 动态高斯系统上的运动特征编解码与恢复实现。
我们保留运动网格查询、MLP 运动预测、逐帧高斯更新和光栅化。
改变的是已量化运动网格的存储表示、GPU 恢复方式和推理状态载入方式。
最终版本不再依靠有损三值截断换取速度。

最终配对参照记为 **4DGC-CL**。它使用我们已落地的闭环训练适配器。
该适配器以客户端解码状态作为下一帧参考，并在保存运动模型后重新查询运动再提交。
不能把这个版本写成“完全未修改的官方 4DGC”，也不能直接套用论文报告的 PSNR。
Flash 与 4DGC-CL 使用相同首帧、相同动态模型、相同新增高斯和 SH 量化包。

我们研究的是已经建模后的场景从磁盘表示恢复到可渲染状态的成本。
它不是从低质量首帧恢复高质量几何的方法，不提高首帧本身的重建能力。
高质量首帧和可靠的相机标定仍由上游提供。

### 2.1 数学定义

令原始编码器已经产生的整数运动特征为 \(z_i\)，最终方法要求它属于 int8 可表示范围。
不是把超范围数强行裁剪进去。当前实现遇到超范围值会拒绝导出。

对每个符号定义：

\[
 m_i=\mathbf 1[z_i\ne0],\qquad s_i=\mathbf 1[z_i<0],\qquad
 r_i=\max(|z_i|-1,0).
\]

将残差展开为位平面：

\[
 r_i=\sum_{b=0}^{B-1}2^b u_{i,b},\qquad
 \hat z_i=m_i(1-2s_i)\left(1+\sum_b2^b u_{i,b}\right).
\]

因此，对支持范围中的整数有 \(\hat z_i=z_i\)。零值不存符号位，长尾不被截断。
无损是相对于原量化整数及 FP32 推理状态，不是相对于原始视频或量化前高斯属性。

每页包含 256 个符号。文件包含形状 Header、页偏移目录和独立对齐页。
页内有 32 字节非零掩码、压紧符号位、每个位平面的控制字节及其数据。
位平面按实际内容选表示：少于 32 个置位位置采用 uint8 局部索引，
一般密集模式使用 32 字节位图，全一模式只写控制码。
控制码 0–31 表示稀疏索引个数，32 表示密集位图，33 表示全一。

这是一种直接可并行寻址的表示选择，不是新熵编码定理。
固定页大小、稀疏索引与位平面本身是已有编码工具，贡献应落到动态运动特征的组合设计与实证收益上。

### 2.2 GPU 执行与边界

细网格解码采用一个 CTA 处理一个 256 符号页。
页目录提供起点，页内通过 `popc` 与 warp 前缀计算定位符号位。
残差平面在共享内存中恢复，线程写出 FP32 网格。
实现使用局部共享内存原子或来组装稀疏位图，并非“完全没有原子操作”。
不同页无需全局前缀扫描或跨 CTA 同步。
整体工作量仍随符号数增长，不应写成整个流 O(1) 解码。

网络参数与空间边界使用 16 字节 Header 和 1805 个 FP32 数，共 7236 字节。
其字段是两层 MLP 权重、偏置以及空间边界。
恢复路径包含主机读取、固定内存缓冲区、H2D 和现有参数张量更新。
这不是“零显存读写”或“解包与光栅化融合”。
恢复后的网格被大量高斯重复查询，因此选择一次恢复、随后复用。

### 2.3 精确性如何进入递归序列

令基线递归状态更新为
\[
 G_t=\mathcal U(G_{t-1}, Z_t,\theta_t,A_t),\quad
 I_t=\mathcal R(G_t,C_t).
\]

其中 \(Z_t\) 为量化运动网格，\(\theta_t\) 为运动 MLP 与边界，\(A_t\) 为新增高斯。
Flash 只替换 \((Z_t,\theta_t)\) 的文件表示和恢复路径。
在初始状态、这些恢复张量、新增包以及后续运算相同的条件下，递归状态无需新增量化扰动。
代码检查整数与 GPU FP32 位级一致性，并独立验证渲染质量。
PSNR、SSIM、LPIPS 相同符合此机制，不需要人为制造不同数字。
这不等价于宣称任意驱动、任意并行实现下所有像素永远位级相同。

## 3. 可写的贡献和不可混入的历史分支

建议以以下三个相互关联的贡献组织，而非宣称三个全新基础算法。

- **精确保留长尾的 GPU 友好运动特征表示。** 对粗细网格采用不同表示，细层通过符号与残差位平面保留大幅特征。当前冻结版本不需要 clip 或刷新兜底。
- **与渲染消费方式一致的恢复路径。** 独立页 GPU 解包后恢复可复用的稠密 FP32 网格，配合连续推理状态载入，缩短从存储到运动推理的准备路径。
- **可核验的质量、存储和时延联合评估。** 用闭环解码参照隔离状态误差，分别报告纯 Kernel、完整恢复和恢复至渲染性能，在指定多场景协议上检验精确转码。

闭环适配是保证实验参照与实际客户端一致的实现条件。
不要将其质量恢复收益全部记成 Flash 编码收益。
也不要声称“比所有同行都快且更小”。当前数据体现不同质量、体积、时延取舍。

历史探索保留在原脚本目录。以下内容不属于最终主方法：

|历史路线|保留价值|最终叙事处理|
|---|---|---|
|删除细网格|说明单帧小变化可能在递归状态中积累|可作动机，不当最终方法|
|三值 clip_1 与 Trit/Sign 打包|证明有损紧凑表示能加速，但质量依场景变化|不再写成冻结主方案|
|周期绝对状态刷新|能修正已经积累的几何误差，代价含状态快照|最终 plane_exact 不启用|
|块位宽与异常表|提供存储设计的负结果与中间方案|只引用同一冻结模型上的可比数据|
|连续 FP32 状态与位平面|最终实现的组成|写入 Method 与主表|

旧探针、旧稀疏初始化和新闭环模型混在一张消融表会混淆因果。
历史实验可叙述“为何转向精确表示”，不能把不同训练模型的差值解释成单模块收益。

## 4. 数据与训练协议

### 4.1 N3DV

六场景为 coffee_martini、cook_spinach、cut_roasted_beef、flame_salmon、flame_steak、sear_steak。
每场景质量覆盖 0–299 共 300 帧，测试相机为 cam00。
当前半分辨率评测为 1352×1014。
固定编码策略跨场景复用，但各场景仍需训练自己的动态模型，不属于零样本泛化。

4DGC-CL 使用 SH degree 1、motion q=1、SH packet q=2、rotate_sh=false。
动态训练每帧 Stage 1 为 400 次，Stage 2 为 100 次。
首帧使用各场景选定的高质量原始 3DGS 模型，运动预热使用该场景自己的边界与点云。
首帧选择与历史修复要在复现设置中披露，不宣称所有场景都用了同一份权重。

3DGStream 的 coffee、salmon、beef 使用经过渲染兼容性验证的共享原始首帧。
cook、sear 使用其稠密初始化修复版本，flame_steak 使用官方提供的初始化流程。
因此这是有明确初始化说明的本地复现，不是所有方法从同一初始点云出发的严格消融。
其动态训练保留对应官方 Stage 1/2 设置及场景自身 NTC 预热。

QUEEN 使用本地正式训练并独立加载的压缩模型。
其 SH degree 为 2，而本次 4DGC-CL/Flash 为 1，质量差异不是只由 codec 决定。
实际保存包中仍包含参考张量、flow、mapping 等字段，这些都计入存储。
没有仅用 entropy byte_stream 的字节数代替完整可加载模型体积。
曾修复三个张量索引位置的 long 类型转换，未改变保存整数类型和算法。

### 4.2 MeetRoom 两场景

本次仅汇报 discussion、trimming，名称写作 **MeetRoom-2 (discussion, trimming)**。
各场景 300 帧、13 个相机，训练 12 个视角，留出 cam_0，分辨率 1280×720。
初始化几何的准备使用了包含留出相机在内的标定/三角化信息。
因此不能描述成“初始化几何也严格排除测试视角”的协议。

4DGC-CL 首帧为 sparse10k，动态配置保持 400/100，运动与 SH 编码设置同上。
Flash 没有为这两个场景添加新网络或更换编码策略。
3DGStream 使用兼容验证后的共享原始首帧和独立 NTC 预热。
QUEEN 使用当前 MeetRoom 适配及自身训练配置，初帧 500 epochs、后续 10 epochs。
这些 epoch 数不能和其他方法的 iteration 数直接当成相同训练预算。

4DGC-CL、Flash、3DGStream 在原 AutoDL RTX 3090 服务器测量。
QUEEN 在另一台克隆环境的 RTX 3090 服务器运行。
GPU 型号一致不代表 CPU、磁盘、缓存和共享负载一致。
跨方法表可汇报该本地测量，但不能声称服务器条件完全受控。
4DGC-CL 与 Flash 的同源配对结果是机制解释的主要依据。

## 5. 指标定义与本次指定选轮规则

### 5.1 质量与存储

每场景先对所有测试帧的 PSNR、SSIM、LPIPS 求均值，再对场景求算术平均。
LPIPS 使用 AlexNet v0.1，RGB 从 [0,1] 映射到 [-1,1]，独立于测速运行。
PSNR 越高越好，SSIM 越高越好，LPIPS 越低越好。

完整场景存储包括首帧、动态包和实际播放所需的共享文件。
单位为十进制 MB，即 bytes/10^6。主表是每个完整场景体积的平均值。
不是平均每帧大小，更不能直接和论文按帧均摊的 Size 数字相减。
诊断全量 PLY、训练日志、重复备份和不用的训练状态不作为 Flash 播放负载。
具体包含哪些文件由各方法的 payload manifest 或 package 统计定义。

### 5.2 时延与合并吞吐

每轮统计帧 1–299 的独立本地恢复至渲染耗时 \(t_{s,r,f}\)。
首帧初始化不进入该逐帧统计。
对选入的所有时间样本集合 \(\mathcal T\)：

\[
 \bar t=\frac{1}{|\mathcal T|}\sum_{t\in\mathcal T}t,\qquad
 \mathrm{FPS}_{\rm pooled}=\frac{1000|\mathcal T|}{\sum_{t\in\mathcal T}t}.
\]

这叫本地解码/恢复与渲染的**合并吞吐 FPS**。
不是训练 FPS，不是纯光栅化 FPS，也不是含网络传输和首帧冷启动的播放器实测 FPS。
不能先平均各场景 FPS，再把结果叫合并吞吐。

P95 从相同样本集合排序后取第 \(\lceil0.95|\mathcal T|\rceil\) 项。
本次所有表统一 nearest-rank 定义，不平均逐场景 P95。
少数极慢帧可以拉高均值，使 P95 低于均值，这在数学上并不矛盾。
所有选入轮次的慢帧仍保留，没有逐帧挑最好值。

Flash 与 4DGC-CL 的范围含文件读取、状态与网格恢复、同步、运动推理、新增高斯拼接、渲染及 GPU 完成。
相机/真值载入、质量指标、编码、JIT、网络传输不计入。
QUEEN 与 3DGStream 采用各自落盘表示到相同测试视角图像的对应路径。
没有人为把整段驻留方法的一次初始化反复算入每帧，也没有使用其论文纯渲染 FPS 代替本地测量。
操作系统缓存未强制清空，所以不是严格冷盘吞吐测试。
QUEEN 的既有计时还保留首次 TorchAC 使用所在帧，详情以各结果的 timing_scope 为准。
这张表比较各方法当前实际可加载表示的回放路径，不声称各方法内部启动行为完全相同。

### 5.3 N3DV 的本次主表

Flash 每场景选择平均耗时较小的一整轮：
\[
 r_s^*=\arg\min_{r\in\{1,2\}}\frac1{299}\sum_{f=1}^{299}t_{s,r,f}.
\]

然后合并六场景选中轮的全部时间样本。
其他三种方法保留每场景两轮，再合并六场景。
当前六个 Flash 场景均选中 timing_2。
FPS、平均耗时、P95 都从同一组被选中的完整轮次计算，不能分别挑最优。
质量与存储不随测速选轮重新挑选。

这满足本次用户指定展示，但它是**不对称选轮展示**，不是相同重复测量估计。
正式论文若保留，表注必须标明 Flash best-of-two，others pooled-two。
不能省略该规则再称“同等测速条件下的无偏加速比”。
末尾保留统一全部两轮合并的敏感性表，供写作窗口对照，不覆盖主展示口径。

### 5.4 MeetRoom 的轮次数

Flash 和 4DGC-CL 当前各场景只有一次这套配对计时。
QUEEN、3DGStream 每场景合并两轮。
不虚构第二次 Flash 测速，也不把 LPIPS 补测当成另一轮速度测量。

### 5.5 GPU 解包时延

`kernel_summary.json` 统计压缩数据已经驻留 GPU 时的 CUDA-event Kernel 时间。
对单网格重复运行取中位数，再把三层网格数值求和，最后对帧/场景取平均。
这是独立测量的解包机制指标，不包括磁盘读取、主机准备、H2D、MLP 和渲染。
它不是完整流水线时间的同义词。
其他方法没有同定义独立算子数据时填缺失，不填 0，也不拿 CPU 熵解码时间顶替。

## 6. 最终结果如何讲

末尾主表直接提供绝对质量、完整存储、合并吞吐、平均耗时、P95 和纯 Kernel 时间。
写作重点是相对于同源 4DGC-CL 保持解码质量，并展示存储代价与恢复速度之间的取舍。
不要把“不新增质量损失”写成“改善场景重建质量”。

N3DV 的 3DGStream 合并吞吐仍高于本次 Flash 主展示值。
因此适合讨论质量、存储和时延的联合位置，不适合声称所有吞吐指标领先。
Flash 的更低 P95 与不最高的 FPS 可以同时成立，它们分别看时间分布分位数和总体耗时。
当前 Flash 体积也高于同源 4DGC-CL。不能写成同时优于基线的压缩率与速度。

MeetRoom 两场景支持固定 codec 在另一类拍摄内容上的适用性。
各场景仍重新训练，结论不是免训练跨数据集泛化。
两个场景结果也不代表尚未纳入的场景都能达到同样质量。

## 7. 建议论文结构

### Introduction

先区分 GPU 光栅化很快与完整存储恢复链路未必快。
指出动态高斯流必须反复恢复运动特征和状态。
本文目标是精确保留既有量化模型的输出，同时降低恢复开销。
用本文的同源配对测量说明问题，不使用历史混合配置的百倍数字替代主表。

### Related Work

按流式动态高斯、动态表示压缩、并行整数/位平面编码三组组织。
4DGC 是母方法，3DGStream 与 QUEEN 是已实测对照。
ADC-GS 等可以作为相关工作，但本次主表没有其已完成测量。
编解码工具的既有出处需写作阶段核对原文，不把经典技巧写成首次发明。

### Method

1. 问题定义与闭环参照。给出递归状态更新、参考包和支持的量化域。
2. 分层运动网格编码。解释粗层稀疏值与细层符号/残差位平面的不同选择。
3. 页内自适应位平面表示。给出控制码、目录、对齐与精确恢复公式。
4. GPU 恢复及连续推理状态。展示 CTA 页面到 FP32 网格、MLP 到光栅化的数据流。
5. 精确性与成本边界。解释不新增量化误差，同时承认目录和非熵表示的存储开销。

### Experiments

1. 设置。数据版本、场景清单、初始化来源、相机、分辨率、GPU/服务器、训练与计时协议。
2. N3DV 主性能表。采用本文件指定选轮，表注明确统计不对称，并附统一两轮对照。
3. MeetRoom-2 表。单独报告，避免把两数据集不同平台结果混成一个“总平均”。
4. 机制表。区分 resident Kernel、H2D+unpack、完整运动恢复与总流水线。
5. 存储分析。粗/细网格、网络状态、首帧和新增高斯占比来自 manifest。
6. 消融。只汇入同一冻结源模型上的格式候选。缺少对应证据的拆分贡献不能编造。
7. 定性图。使用真实相同测试视角输出，不能为制造“有差异”修改图像或指标。

### Limitations / Discussion

基于特定 4DGC 网格布局和量化域，尚非任意 4DGS 的通用压缩器。
不修复差首帧、不保证压缩率优于熵编码、不消除运动推理与光栅化成本。
本地文件测量不含网络/首帧启动，测速轮数与平台差异按表注限定。
无需为了完成该交接新增实验或声称已经完成未做的消融。
